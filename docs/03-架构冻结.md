# 阶段 0 交付物 3：冻结整体架构与依赖关系

> 本文档描述的架构自阶段 0 结束即冻结。任何变更须先提交变更方案（原因、影响范围、替代方案、迁移成本），经确认后修改本文档再改代码。

## 1. Workspace 布局

```
sts-rs/
├── Cargo.toml            # [workspace] members = ["crates/*"]
├── crates/
│   ├── sts-data/         # 静态数据 + 纯函数（RNG/文本/ID/常量）
│   ├── sts-core/         # 游戏状态、规则、流程（核心逻辑，零 UI/平台依赖）
│   ├── sts-interface/    # 核心视图 GameView + 玩家命令 PlayerCommand 协议
│   ├── sts-terminal/     # 终端渲染 + 输入 + main 可执行入口
│   └── sts-tests/        # 跨 crate 规则测试 / 回归 / 对照 / 流程测试
├── docs/                 # 本文档体系
└── saves/                # 运行期生成（gitignore）
```

## 2. 依赖关系（强制单向）

```
sts-terminal ──▶ sts-interface ──▶ sts-core ──▶ sts-data
                      ▲                ▲
                      │                │
sts-tests ────────────┴────────────────┘（依赖全部；无人依赖 tests）
```

规则：
1. **sts-core 不依赖** sts-interface / sts-terminal、任何终端尺寸/颜色/按键概念、任何平台 API。
2. sts-data 不依赖任何其他 crate（甚至 std 之外最少化：不引入 serde 等重量依赖；文本表用 `&'static str`）。
3. sts-interface 只定义数据结构（View/Command/Result）与 serde 派生，可依赖 sts-core 的**类型**（ID 枚举）但不 import sts-core 行为模块——若出现循环，把共享类型下沉到 sts-data。
4. sts-terminal 只通过 sts-interface 与核心交互；禁止直接 `use sts_core::state::*` 修改状态。
5. 外部依赖白名单（跨平台硬约束，见 docs/08）：
   - `crossterm`（终端 raw mode / 事件 / ANSI 输出，Windows VT + Unix 原生）
   - `serde` + `serde_json`（存档/协议）
   - `unicode-width`（文本宽度计算，中英文混排）
   - 测试用：`insta` 或纯 assert（不引入快照大件也行，按需）
   - 禁止：任何 platform-specific crate（winapi 直接调用、objc 等）。

## 4. 核心运行时模型（冻结决策）

### 4.1 单线程 + 显式 tick

- 无全局可变静态（不用 thread_local / lazy_static 承载游戏状态）。整个游戏状态根为 `Game`，由入口持有。
- 核心暴露两种驱动方式：
  - `Game::tick()`：推进一个逻辑步（相当于原版一帧的 update，动作时长归零处理）；
  - `Game::run_until_idle()`：循环 tick 直到进入 `WaitingOnUser`（用于测试与批量模拟）。
- RNG 顺序敏感性要求：**一切影响状态的随机调用发生在 tick 内的确定位置**；UI 不产生随机。

### 4.2 动作系统（原版语义 1:1）

- `enum GameAction { Damage(DamageActionData), GainBlock(..), ... }`，字段对齐原版（duration → `Duration` 枚举：Instant/Short/Long，仅作队列屏障标记）。
- 队列：`actions: VecDeque`、`pre_turn: VecDeque`、`card_queue: Vec<CardQueueItem>`、`monster_queue: VecDeque` + `monster_attacks_queued: bool` + `turn_has_ended: bool` + `phase`。
- `add_to_top/bottom/turn_start/next_combat` 四个入口，**非 COMBAT 静默丢弃语义保留**（战斗外等价通道走直接调用）。
- 首帧/等待帧统一建模：`phase: Setup, Active, Done`（替代浮点 duration 比较，记录 09 风险 3）。

### 4.3 借用模型（解决 Java 交叉引用）

原版大量双向引用（card↔queue、action↔creature、relic→deck card）。Rust 对策：
- 实体以**索引/uuid 定位**（CardUuid、MonsterIndex、PowerSlot），不存 Rust 引用；
- `GameAction` 变体携带 id，`update` 时从 `&mut Game` 现场解析；
- CardQueueItem 持 CardUuid；limbo 概念保留为 CardGroup 类型之一。

### 4.4 数值语义（冻结）

- 全部伤害链使用 `f32` 计算，末端 `floor`（与 MathUtils.floor 对齐）；中途 int 截断点逐处保留（背击 ×1.5、Lockon ×1.5）。
- 哨兵建模：`cost: Cost` 枚举（Fixed(u8)/X/Unplayable）；base 数值 `i32`，-1 语义保留为"未使用"并配合 `has_damage: bool` 防误算（见 docs/07 D-04）。
- 格挡/能量/生命边界钳制按原版常量（999/999/1）。

### 4.5 洗牌与随机派发表（冻结）

| 场景 | 原版调用 | Rust 派发 |
|---|---|---|
| 战斗开局 initializeDeck | shuffleRng | rng.shuffle |
| 弃牌堆洗回 | shuffleRng（EmptyDeckShuffleAction） | rng.shuffle |
| 卡牌随机选取（getRandomCard(useRng=true)） | cardRng | rng.card |
| 战斗中随机弃牌 / addToRandomSpot / Strange Spoon / randomTarget | cardRandomRng | rng.card_random |
| 怪物 AI rollMove / HP / 构造掷点 | aiRng / monsterHpRng / miscRng | rng.ai / rng.monster_hp / rng.misc |
| 遭遇队列 | monsterRng | rng.monster |
| 事件 | eventRng | rng.event |
| 商店 | merchantRng | rng.merchant |
| 卡奖励稀有度 | cardRng | rng.card |
| 宝箱/战后金 | treasureRng | rng.treasure |
| 遗物 | relicRng | rng.relic |
| 药水 | potionRng | rng.potion |
| JDK shuffle 场景 | java.util.Random(seed) | jdk::Random（独立算法） |

## 5. UI 分离契约（冻结）

- 核心不感知终端。核心向 UI 提供的两个入口在 sts-interface 中定义：
  - `view(game: &Game) -> GameView`：按当前 Screen 给出完整、可渲染的状态快照（含所有可选项与禁用原因）。
  - `apply(game: &mut Game, cmd: PlayerCommand) -> CommandResult`：提交玩家操作；核心负责全部校验、结算、随机。
- `CommandResult` 返回：接受/拒绝（含原版等价的 cantUseMessage）、日志条目、是否需要 view 刷新。
- 核心 `flow` 模块管理 Screen 状态机（23 屏 + 返回栈），UI 依据 `GameView.screen` 切换面板。

## 6. 错误与异常

- 原版无异常控制流（EmptyDeckShuffleException 不存在于本源码）；核心用 `Result<T, CoreError>` 于协议边界，内部以状态机推进。
- 不变量违反（如 HP<0 未钳制）用 `debug_assert!` 捕获，release 保持原版宽松行为。
