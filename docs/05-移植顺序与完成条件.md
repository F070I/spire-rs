# 阶段 0 交付物 5：分模块移植顺序及每个模块的完成条件

> 顺序即依赖序（自底向上），不是重要度。每个模块完成时在 docs/modules/<模块>.md 记录：实现位置、验证依据（原版文件+行为）、测试结果、已知差异。

## 通用完成条件（每个模块都必须满足，下称【完成条件】）

1. 全部对应机制（docs/01 中该模块的条目）已实现，无静默简化。
2. 时序保真点（docs/02 §3.4）逐条核对并在模块记录中打勾。
3. 单元测试覆盖：正常路径 + 边界（0/-1/999/溢出）+ 触发顺序 + 异常输入。
4. 种子回归测试（若模块含随机调用）：固定种子断言完整输出序列。
5. `cargo test -p <crate>` 通过；`cargo clippy` 无 error。
6. 模块记录文档完成，含"未完成/存疑"标记（如无则写明"无"）。

## 批次间验证门（Gate）

- G1（批次 1 后）：RNG 向量测试与 JDK 兼容测试通过（能用参考实现比对）。
- G2（批次 2 后）：**机制沙盘测试**——用 5 张测试卡 + 1 个测试怪打完整战斗：能量/抽弃耗洗/伤害链/回合钩子顺序断言全过。
- G3（批次 3 后）：全卡冒烟——每张卡在有/无目标、升级/未升级、双支持遗物场景下不 panic 且产出正确动作序列（脚本化）。
- G4（批次 4 后）：**整局种子回归**——固定种子跑 50 层自动脚本（贪心 AI），存档/读档 round-trip 后状态完全一致。
- G5（批次 5 后）：解锁/进阶/每日影响点回归通过。
- G6（批次 6 后）：三平台人工验收（docs/08 §测试矩阵）+ 体积达标。

## 明确不做的"顺序借口"

- 不允许"先不做 Watcher/先不做 Act 4"——批次内条目全部完成才算批次完成；批次间允许暂停，但冻结范围不变。
- 内容灌注（批次 3）可与批次 4/5 的机制工作由不同会话并行，前提是架构冻结不变。
