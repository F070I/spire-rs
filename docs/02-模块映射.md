## 2. 静态数据 → sts-data

原版静态数据分散在：类构造器（数值/标志）、`localization/*Strings.java`（内嵌 JSON 文本）、RelicLibrary/CardLibrary 的注册代码、MonsterHelper/EventHelper 的工厂表。

Rust 侧规划：

- `sts-data::ids`：全部卡牌/遗物/药水/怪物/能力/事件/遭遇 key 的常量表（String → enum 或 `&'static str` 常量）。**原版 ID 字符串是硬契约**（存档、本地化键、hasRelic 字面量判断都依赖），因此保留原字符串作为规范 ID，另建类型安全句柄。
- `sts-data::cards`：每张卡的静态面（id、名称 key、cost、type、rarity、color、target、baseDamage/Block/MagicNumber、exhaust/ethereal/innate/retain 标志、描述模板、升级 delta）。以数据表 + 少量代码生成（proc-macro 或构建脚本不引入；用普通声明宏或直接手写常量表）。
- `sts-data::relics/potions/monsters/events`：同上静态面。
- `sts-data::text`：本地化字符串（优先英文 KeyStrings；中文界面文本从 localization 中文 JSON 提取为常量表）。关键词表（GameDictionary）。
- `sts-data::encounters`：遭遇表（弱/强/精英/Boss 池与权重、MonsterHelper 工厂映射、generateExclusions 互斥表）。
- `sts-data::rng`：RandomXS128 + JDK Random 两个纯算法实现（无依赖、可独立 fuzz 测试）。
- `sts-data::config`：数值常量（MAX_HAND_SIZE=10、NUM_POTIONS=3、地图参数、掉落率、篝火 30%、商店 jitter 等，出处记录 05/07/08）。

原则：**sts-data 不含行为**，只有数据与纯函数（RNG、文本解析、ID 映射）。

## 3. 行为层 → sts-core

### 3.1 状态模型（替代原版 static 海）

```
sts_core::state::{
  Game,          // 顶层：模式机 + 当前 Run + prefs 等价物
  RunState,      // 一局：player, actNum, floorNum, rngs{12}, dungeon, map, path…
  DungeonState,  // 幕：map, currMapNode, pools(卡/遗物/事件/遭遇), bossKey…
  BattleState,   // 一场战斗：monsters, action queues, counters, souls 等价物
  ScreenStack,   // Screen 枚举 + previous_screen + swap 标志（见 docs/04 §Screen）
}
```
原版 `AbstractDungeon` 的 ~150 静态字段按上面四层归位；`CardCrawlGame.dungeon` 自引用取消，由 `Game.run` 持有。

### 3.2 对象模型决策（trait + enum 混合）

- **Card**：`enum CardKind`（447 变体）持有静态数据句柄 + 实例字段（upgraded、misc、uuid、costForTurn 等）；效果通过 `impl CardKind` 的 match 实现 use/upgrade/钩子。理由：动作队列与存档需要值语义与可序列化；dyn trait 无法满足 Copy/Serialize 与 makeCopy 语义。钩子默认实现走 trait `CardHooks`（`impl DefaultHooks for CardKind` match 派发）。
- **Power**：`enum PowerKind`（~162 变体）+ 实例 `amount`、priority、标志。钩子 trait `PowerHooks`，默认空实现，逐 kind 实现。
- **Relic**：`enum RelicKind`（177）+ counter/grayscale 等实例状态。
- **Monster**：`enum MonsterKind`（73）+ `MonsterCore`（HP/block/powers/damage 列表/move state/自定义字段 union 或 `Box<MonsterSpecific>`）。
- **Event**：`enum EventKind`（~50）+ screenNum 状态机。
- **Action**：`enum GameAction`（~280 变体，每变体携带参数），`update()` 用 match。不再用 Java 继承。
- 钩子遍历顺序逐条按记录 03/06/09 的表实现，写成核心内的固定派发函数（如 `damage_player_pipeline`），不散落。

### 3.3 模块依赖图（crate 内，自上而下单向）

```
state ──▶ action ──▶ { card, power, relic, potion, monster, orb, stance }
   │            │              │
   │            └──────◀───────┘   （效果产生动作，动作操作实体）
   ├─▶ { dungeon, map, room, reward, shop, event, neow, blight }
   ├─▶ { save, unlock, metrics, mod, trial, helper }
   └─▶ data（RNG、常量、ID、文本）
```

### 3.4 时序保真要点（移植时必须对照的时序表）

1. 打卡全链时序：记录 09 §1 总钩子顺序一览。
2. 回合开始/结束序列：记录 01 §3/§8。
3. 玩家 vs 怪物 damage() 管线差异：记录 03 §5。
4. 抽牌/洗牌/弃牌/消耗钩子序：记录 09 §4-6。
5. 战斗开始 16 步 / 战斗结束序列：记录 09 §9。
6. nextRoomTransition 全序：记录 01 §7 / 05 §4。
7. ApplyPowerAction 分支序：记录 09 §8。
8. 事件二段解析（'?' 房）：记录 05 §4 第 6 步。

**动作时长处理**：原版每个 action 有 duration（帧延时）。Rust 核心用"逻辑步"模型：`tick()` 推进当前动作至下一个"需要等待"点；带 duration 的动作在其等待帧直接完成（等价于 FAST_MODE=0 但保持队列屏障语义）。UI 层需要演出节奏时可对 `BattleState` 逐步 tick 并渲染中间态。

## 4. UI 层 → sts-interface + sts-terminal

- sts-interface 定义协议（docs/04）；核心暴露 `UiBridge`：`view(&Game) -> GameView`（完整快照视图）与 `apply(&mut Game, PlayerCommand) -> CommandResult`。
- 原版 screens/ 的交互语义全部折算为 PlayerCommand（清单见记录 08 §8）；Screen 状态机保留在核心（flow），终端只渲染。
- 原版 vfx 的逻辑副作用对应核心即时结算；终端无需动画。

## 5. 存档格式策略（决策 D-01）

- 首选：自定义 JSON 结构，字段名与语义对照原版 SaveFile（含 RNG counter 全集——原版漏存的 monster_hp 等 counter 属反编译噪声，按"可复现优先"补全，见 docs/07 D-02）。
- 不承诺兼容原版存档文件（ XOR+Base64 可解码，但 Gson 字段语义复杂；列入风险清单 R-06，作为可选后续目标）。
- 混淆保留为可选项（默认明文 JSON，便于测试与调试）。
